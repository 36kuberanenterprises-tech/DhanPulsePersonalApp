# DhanPulse Build 85 code audit and verification record

Date: 18 November 2026

## Scope and audit method

Reviewed source branches rather than the live server or an installed phone. Android source reviewed: MainActivity.kt, FlowScreen.kt, DhanPulseViewModel.kt, Api.kt, LivePriceStream.kt, MarketMonitoringService.kt, MarketMonitorStore.kt, SecurePrefs.kt, AndroidManifest.xml, build.gradle.kts and the APK workflow. Backend source reviewed: angel.js, history-control.js, server.js, flow-monitor.js, live-stream.js, stock-scanner.js, backtest.js, candle-store.js, and backend regression tests. The branches have diverged and are not a single integrated production deployment. This is a static code audit with CI tests, **not** a live end-to-end certification.

## Confirmed code observations

1. Android's market streaming client consumes authenticated Server Sent Events from /api/live/:symbol/stream. The stream uses a 45 second read timeout and Build 84 detects 90 seconds without a LIVE quote while receiving other events. The ViewModel reconnects with a bounded retry delay.
2. Build 84 added a ConnectivityManager callback for default network changes and a validated network check. This is transport agnostic and works with usable 3G, 4G, 5G, WiFi and hotspots, subject to Android, VPN, carrier and server reachability. Neither code review nor CI tests prove network switching on a real device.
3. Before Build 85, MainActivity could show generic DELAYED while the stream status had a more specific connection diagnosis. Build 85 prioritises NETWORK OFFLINE, SERVER UNREACHABLE, SESSION EXPIRED and RECONNECTING for appropriate trading screens.
4. Build 85 avoids repeated foreground scanner and analysis polling while Android reports no validated internet; foreground reconnect restarts the selected market stream and refreshes analysis.
5. FlowScreen polls its snapshot independently from the main market SSE client. Backend Flow uses a separate broker socket with bounded reconnection. A main SSE fix does not certify Flow recovery.
6. Android's optional background MarketMonitoringService has its own loops and an explicit service runtime budget. This can stop on Android's foreground-service time limit. No APK code can guarantee continuous operation when Android limits or kills its service.
7. The backend deliberately requires broker-confirmed OHLCV for trade decisions and treats stale snapshots as unsafe. The application must not synthesise prices or remove trading safeguards.
8. Angel One /historical/v1/getCandleData HTTP 403 is not resolved by the mobile connectivity changes. The shared HistoryBudget applies cooldown across local historical callers. Other processes, applications and broker account limits are invisible to that local limiter.
9. The Azure diagnostic branch supplies an authenticated read-only history endpoint and durable broker-confirmed candles. The newer separate HTTP 403 diagnostics branch classifies historical rejections and reports the configured outgoing IP header versus known observed egress. Neither branch has been confirmed deployed on Windows Azure.
10. The backend has a fallback public IP header used when CLIENT_PUBLIC_IP is not set; compare it against the current Azure route privately. Do not change registered IPs based on a guess.
11. Build 85 is a separate debug-preview package with a distinct suffix and cannot update or share the secure data of the existing stable app. Stable signing compatibility must be separately confirmed.

## Change set

Build 84 included network recovery and a stalled SSE watchdog. Build 85 extends the app status display and skips ineffective polling while Android is offline. No broker credentials, registered IP, order permissions or live Azure process were changed.

## Safe next production steps

1. Inspect the running Azure commit, current service and private route, avoiding any public credential disclosure.
2. Deploy the compatible backend diagnostic branch through the existing Windows process with a rollback plan.
3. Read the authenticated /api/diagnostics/history endpoint to check last rejection, actual cooldown and the configured outgoing public IP header.
4. Make one controlled fresh historical candle request only after the cooldown, with a valid token and date range, and capture the precise HTTP status, broker error code and timestamp.
5. If a 403 still occurs at low request frequency with valid credentials, ask SmartAPI support to check entitlement and account-side throttling. Do not bypass the restriction.
6. Check Android installation, certificate, mobile handoffs, Tailscale connection, SSE freshness, scanner, Flow and background behaviour on a real phone before calling the system stable.

This record does not imply that every defect in the repository has been located, and does not convert automated compilation into a live market certification.
